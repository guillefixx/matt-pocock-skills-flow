1. /implement-spec — De ser el "bucle for humano" a un Orquestador de Grafo Paralelo — From being the "human for-loop" to a Parallel Task Graph Orchestrator

Engineering · Parallel Build

Antes de v1.3, si una spec tenía 6 tickets, tenías que abrir 6 sesiones manuales, hacer /implement y /clear una por una. /implement-spec delega ese despacho a un agente orquestador que lee los tickets como un grafo de tareas (task graph) guiado por las aristas de bloqueo de /to-tickets.

Before v1.3, if a spec had 6 tickets, you had to manually run 6 sessions, calling /implement and /clear one by one. /implement-spec hands dispatching to an orchestrating agent that reads tickets as a task graph driven by the blocking edges from /to-tickets.

A) Frontera Lista (Frontier) A) Ready Frontier

Calcula qué tickets tienen todos sus bloqueadores resueltos y lanza un subagente implementador para cada ticket de la frontera a la vez.

Finds all tickets whose blockers have landed and spawns an implementer subagent for every ticket on the frontier at once.

B) Worktrees + Punteros B) Worktrees + Pointers

Cada subagente corre en su propio git worktree basado en la rama de integración y se comunica mediante punteros de contexto (notas de exploración compartidas) para no saturar al orquestador.

Each subagent works in its own git worktree based on the integration branch and talks via context pointers (shared exploration notes) to keep prompts small.

C) TDD + Fast-Forward C) TDD + Fast-Forward

Cada subagente construye con /tdd (Red-Green), fusiona la punta de la rama de integración en su rama y aterriza mediante fast-forward merge, desbloqueando nuevos tickets.

Each implementer drives /tdd (Red-Green), merges the integration branch tip into its own branch, and lands via fast-forward merge, unlocking downstream tickets.

D) Review Único al Final D) Single End Review

Cuando todos los tickets aterrizan, ejecuta /code-review una sola vez sobre la rama de integración completa y envía los hallazgos a un subagente corrector. Funciona también 100% offline.

Once every ticket has landed, runs /code-review once over the integration branch and sends findings to a fix subagent. Works 100% offline on local trackers too.

⚠️
Cuidado con las colisiones en archivos compartidos: Los worktrees posponen las colisiones al momento del merge. Si dos tickets paralelos tocan el mismo archivo de tipos o catálogo de mensajes, añade una arista de bloqueo entre ellos o fija los nombres exactos en las notas de exploración. Watch out for shared-file collisions: Worktrees postpone collisions to merge time. If two frontier tickets touch a shared config or type file, add a blocking edge between them so they run sequentially, or pin exact names in the shared exploration notes.

2. /pr — La anatomía de una Pull Request pensada para el cerebro humano — The shape of a Pull Request built for human reviewers

Reference Skill · Model-Invoked

/pr es una skill de referencia que el agente carga automáticamente siempre que redacta una PR. Sustituye los muros de texto por tres secciones en orden estricto:

/pr is a format reference skill that the agent loads automatically whenever writing a PR body. It replaces walls of text with three sections in strict order:

1. Summary (Visual First)

Empieza directamente en ## Summary sin introducciones. Muestra la forma del cambio mediante 1 vista visual compacta (pseudocódigo, call tree, árbol de componentes, árbol de archivos, Mermaid o shaped diff).

Starts right at ## Summary with zero preamble. Shows the shape of the diff using the smallest clear visual (pseudocode, call tree, component tree, file tree, Mermaid, or shaped diff).

2. Evidence (Before & After)

Decir "los tests pasan" no es evidencia. Exige un antes y después verificable: captura de pantalla en cambios visuales, o el test exacto en pseudocódigo que antes fallaba y ahora pasa.

Saying "tests are green" is a claim, not evidence. Requires a before and after: a screenshot for visual changes, or the exact test that failed before and passes now / console output change.

3. Merge Danger (Door + Blast Radius)

Clasifica el cambio como Two-way door (barato de revertir) o One-way door (migración destructiva, borrado, envío de emails, API pública) y nombra su Blast Radius (qué se rompería si falla).

Grades the change as a Two-way door (cheap to reverse) or One-way door (destructive migration, sent emails, public API removal) and names its Blast Radius (what breaks if wrong).

🔒 El Contrato Inmutable de Ejecución The Immutable Execution Contract

"It never reopens the plan. There is no interview, no clarifying round, no proposal of a different approach. Whatever was settled upstream is the input, and the skill's whole job is to turn that into a commit."

Las fases /grill-with-docs, /to-spec y /to-tickets ya son tu planificación. Si activas el modo plan nativo antes de implementar, el agente ignorará el contrato y volverá a rediseñar la arquitectura sobre la marcha.

/grill-with-docs, /to-spec, and /to-tickets are your planning phase. Activating built-in plan mode before implementing nudges the agent to redesign the architecture while building it.
